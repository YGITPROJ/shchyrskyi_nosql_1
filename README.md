1. Чому аудіо-характеристики винесені в окремий об’єкт audio_features?
Логічне групування: Це дозволяє відокремити метадані треку (назва, альбом) від технічних характеристик звуку. Код стає чистішим, а структура — зрозумілішою.

Вигода: Таке вкладення зручне, коли ми часто завантажуємо або обробляємо ці фічі разом (наприклад, для подачі в модель машинного навчання). Також це дозволяє легко створювати індекси на весь об'єкт.

Проблеми: Якщо об'єкт занадто великий або рівнів вкладеності занадто багато, це може ускладнити написання запитів (потрібно постійно вказувати шлях через крапку audio_features.tempo).

2. Чому виконавці зберігаються як масив, а не як рядок?
Простота запитів: Тепер ми можемо легко знайти всі треки конкретного артиста (наприклад, за допомогою $in або простого фільтра), навіть якщо він не є першим у списку.

Агрегація: Ми можемо використовувати $unwind, щоб порахувати кількість треків для кожного окремого виконавця або згрупувати дані за артистами. Рядок із розділювачем ; змушував би нас використовувати складні регулярні вирази, які працюють повільно.

3. Що таке $out і чим він відрізняється від $merge?
$out: Повністю переписує цільову колекцію. Якщо вона існувала, вона буде видалена і створена заново з результатами агрегації. Використовується для створення "знімків" даних або при повній трансформації.

$merge: Дозволяє комбінувати результати агрегації з існуючими документами в колекції. Він може оновлювати окремі поля, додавати нові документи або ігнорувати існуючі.

Коли використовувати: $out — для повної ідемпотентної перезапису (як у нашому ДЗ). $merge — для інкрементальних оновлень великих колекцій без їх повного перестворення.

1. Для чого використовується інструкція $unwind?Оператор $unwind використовується для "розгортання" масивів. Кожен документ, що містить масив (наприклад, artists: ["A", "B"]), перетворюється на кілька окремих документів (один з "A", інший з "B").Навіщо: Це необхідно для агрегації за окремими елементами масиву. Без $unwind ми б рахували статистику для комбінації артистів, а з ним — для кожного виконавця персонально.
2. Чим $stdDevPop відрізняється від $stdDevSamp?Обидва оператори розраховують стандартне відхилення (міру того, як сильно дані розкидані від середнього значення):$stdDevPop (Population): Розраховує відхилення для всієї генеральної сукупності. Використовується, коли у тебе в базі є всі дані (як у нашому випадку — весь датасет).$stdDevSamp (Sample): Розраховує відхилення для вибірки. Математично він використовує корекцію Бесселя (ділить на $n-1$). Використовується, якщо ти аналізуєш лише маленьку частину даних, щоб оцінити загальну картину.

1. Про фільтрацію кількості треків виконавця (Запит 1)
Якщо знизити поріг до 1: У Топ-10 потраплять "артисти одного хіта" або акаунти, що завантажили лише один трек із максимальною популярністю (100). Результат буде статистично "шумним" і не відображатиме реальний вплив артиста на індустрію.

Якщо підвищити поріг до 50: Список різко зміниться на користь суперзірок (наприклад, Taylor Swift, Drake, Bad Bunny). Це відсіє нішевих артистів і залишить лише тих, хто має величезну дискографію та стабільно високу популярність протягом років.

2. Про фільтрацію кількості треків у жанрі (Запит 3)
Чи зміниться результат при зниженні до 50: Так, результат може зміститися. При низькому порогу (50 треків) у топ можуть вирватися дуже специфічні або рідкісні мікро-жанри, які мають аномально високі показники танцювальності через малу вибірку.

Пояснення: Поріг у 100 документів діє як "закон великих чисел" — він згладжує випадкові відхилення окремих треків і показує справжню характеристику жанру в цілому. Статистична надійність результату зростає разом із розміром вибірки.

Завдання 1: Що змінилося в плані виконання?
Тип сканування: До створення індексу в полі stage було значення COLLSCAN (Collection Scan) — база перевіряла кожен документ. Після створення індексу з'явився IXSCAN (Index Scan).

Кількість перевірених документів: Поле totalDocsExamined різко зменшилося. Якщо раніше воно дорівнювало загальній кількості треків у базі, то тепер воно близьке до кількості знайдених документів (nReturned).

Сортування в пам'яті: До індексу ми бачили стадію SORT, що означало сортування результатів у оперативній пам'яті сервера. З індексом { popularity: -1 } база бере дані вже відсортованими, що економить ресурси.

Як зрозуміти, що індекс працює?
Потрібно дивитися на об'єкт executionStats. Основні маркери успіху:

winningPlan.queryPlan.stage: має бути FETCH -> IXSCAN.

totalKeysExamined: кількість перевірених ключів індексу.

totalDocsExamined: кількість завантажених документів (має бути мінімальною).

Завдання 3: Чи є запит покривним (covered query)?
Запит:

JavaScript
db.tracks.find({ track_genre: "pop", popularity: { $gte: 70 } });
Відповідь: НІ, цей запит НЕ є покривним.

Обґрунтування:

Визначення: Запит вважається покривним лише тоді, коли MongoDB може отримати всі необхідні дані (і для фільтрації, і для виводу) безпосередньо з індексу, не звертаючись до самих документів на диску.

Проблема виводу: Наш запит не має другої частини — проєкції. За замовчуванням MongoDB повертає всі поля документа (_id, track_name, audio_features тощо). Оскільки цих полів немає в нашому індексі, база змушена йти на диск і читати документ (стадія FETCH).

Як зробити його покривним? Потрібно додати проєкцію, яка залишить лише ті поля, що є в індексі, і вимкнути _id:

JavaScript
db.tracks.find(
  { track_genre: "pop", popularity: { $gte: 70 } },
  { _id: 0, track_genre: 1, popularity: 1 } // Тільки ці поля є в індексі
);
